================================================================================
 SEO Blogs — /api/blogs test curls
 Endpoints under test:
   GET  /api/blogs   -> validation criteria / patterns for the JSON payload
   POST /api/blogs   -> ingest a post (validate -> quality gate -> publish/flag)
   GET  /api/admin/settings  -> read auto-publish toggle
   PATCH /api/admin/settings -> toggle auto-publish
   POST /api/admin/upload    -> upload image to Cloudinary
================================================================================

SETUP
--------------------------------------------------------------------------------
1. Start the dev server (from the repo root):
     bun dev
   Default base URL: http://localhost:3000

2. Set your API key + base URL as shell variables (adjust as needed).
   The key must match INGEST_API_KEY in your .env.local — note that value is
   stored there wrapped in double quotes (INGEST_API_KEY="..."), don't include
   the quote characters when you copy it:

     export BASE_URL="http://localhost:3000"
     export INGEST_API_KEY="paste-the-unquoted-value-from-.env.local-here"

3. This folder contains 6 ready-to-use payload files (already verified
   against the real quality-gate logic, not hand-guessed):
     good_payload.json    - passes every quality check   -> stored "published"
     legacy_payload.json  - same as good but with legacy content_body shape
                             -> stored "published" (proves content_body works)
     draft_payload.json   - passes every check, but status:"draft" was
                             explicitly requested -> stored "flagged" anyway
     thin_payload.json    - schema-valid but fails 5 quality checks
                             (too short, no FAQ/takeaways, etc.) -> "flagged"
     invalid_payload.json - missing required fields entirely -> 422, never
                             reaches the quality gate
     modular_payload.json - uses content_sections (3 sections), images gallery,
                             and external_links -> stored "published"

   Run curls from *this* directory so the `-d @file.json` paths resolve.

4. For admin API tests (settings/upload), you need a session cookie.
   Log in at http://localhost:3000/admin/login, then copy the admin_session
   cookie from your browser's dev tools and set:

     export ADMIN_COOKIE="admin_session=<paste-the-cookie-value-here>"

================================================================================
 TEST 1 — GET /api/blogs, no API key -> 401 Unauthorized
================================================================================
curl -i "$BASE_URL/api/blogs"

Expect: HTTP 401, body {"error":"Unauthorized"}


================================================================================
 TEST 2 — GET /api/blogs, with API key -> 200 OK, full spec
================================================================================
curl -s -H "x-api-key: $INGEST_API_KEY" "$BASE_URL/api/blogs" | jq

(drop the `| jq` if you don't have jq installed — raw JSON still prints fine)

Expect: HTTP 200 with:
  - request_schema       JSON Schema generated live from the Zod payload
                          schema (src/lib/validation.ts) — field types,
                          required/optional, regex patterns (slug, UUID,
                          ISO datetime, URL), enums, etc.
  - quality_gate.checks   the 7 automated checks that decide auto-publish
                          vs. flagged-for-review, with their thresholds
  - responses             what 201 / 401 / 409 / 422 look like

Same request also works with the Bearer form instead of x-api-key:
curl -s -H "Authorization: Bearer $INGEST_API_KEY" "$BASE_URL/api/blogs"

================================================================================
 TEST 4 — POST /api/blogs, empty/garbage body -> 422 Validation failed
================================================================================
curl -s -X POST "$BASE_URL/api/blogs" \
  -H "x-api-key: $INGEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d @invalid_payload.json | jq

Expect: HTTP 422, body:
  { "error": "Validation failed", "issues": [ { "field": "...", "message": "..." }, ... ] }
One issue per missing/invalid required field (agent_content_id, slug,
primary_keyword, tags, author_id, content_body, featured_image, og, ...).


================================================================================
 TEST 5 — POST /api/blogs, clean payload -> 201 Created, status "published"
================================================================================
curl -s -X POST "$BASE_URL/api/blogs" \
  -H "x-api-key: $INGEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d @good_payload.json | jq

Expect: HTTP 201, body:
  {
    "id": "<uuid>",
    "slug": "ultimate-content-marketing-strategy-guide-2026",
    "status": "published",
    "quality_report": { "passed": true, "checks": [ ...8 checks, all passed... ] }
  }

This payload requests status:"published" and clears every quality check
(title 54 chars, meta description 144 chars, primary_keyword in title/first
paragraph/image alt, 1116-word body, unique slug/title, 3 key_takeaways +
2 faq entries, no source_trend_reference so the difficulty guard is skipped),
so it auto-publishes with no human review.

Side effect worth knowing: on a real publish this also fires IndexNow /
Google Indexing pings and revalidates cached pages (src/lib/publish-hooks.ts).
Those calls are fire-and-forget and only log a warning if INDEXNOW_KEY /
GSC_SERVICE_ACCOUNT_JSON aren't configured — they won't fail the request.

================================================================================
 TEST 7 — POST /api/blogs, explicit status:"draft" -> 201, status "flagged"
================================================================================
curl -s -X POST "$BASE_URL/api/blogs" \
  -H "x-api-key: $INGEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d @draft_payload.json | jq

Expect: HTTP 201, "status": "flagged", "quality_report.passed": true (all 8
checks pass — this is a different, unique title/slug from good_payload.json
so it doesn't also trip the near-duplicate-title check).
Demonstrates that a passing quality report is NOT enough to auto-publish —
an agent can still force human review by submitting status:"draft".


================================================================================
 TEST 8 — POST /api/blogs, thin/low-quality content -> 201, status "flagged"
================================================================================
curl -s -X POST "$BASE_URL/api/blogs" \
  -H "x-api-key: $INGEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d @thin_payload.json | jq

Expect: HTTP 201 (schema is valid, so it's still accepted and stored), but
"status": "flagged" and "quality_report.passed": false, with these checks
failing: title_length, meta_description_length, primary_keyword_placement,
content_word_count, aeo_extractability. Shows the difference between a
*rejected* payload (422, TEST 4) and an *accepted-but-flagged* one (this).


================================================================================
 TEST 9 — POST /api/blogs, modular payload (content_sections) -> 201
================================================================================
curl -s -X POST "$BASE_URL/api/blogs" \
  -H "x-api-key: $INGEST_API_KEY" \
  -H "Content-Type: application/json" \
  -d @modular_payload.json | jq

Expect: HTTP 201, body:
  {
    "id": "<uuid>",
    "slug": "advanced-keyword-research-techniques-modern-seo-2026",
    "status": "published",
    "quality_report": { "passed": true, "checks": [ ...8 checks, all passed... ] }
  }

This payload uses content_sections (3 titled sections, each with markdown
content and optional images), a gallery (2 images), and external_links (2
entries). It omits content_body entirely — the pipeline picks up content
from content_sections[].content. Section IDs are server-generated by
slugifying each section title. The section_heading_discipline check verifies
no section content starts with a top-level (# or ##) heading.

================================================================================
 TEST 12 — PATCH /api/admin/settings -> toggle auto-publish off
================================================================================
curl -s -X PATCH "$BASE_URL/api/admin/settings" \
  -H "Cookie: $ADMIN_COOKIE" \
  -H "Content-Type: application/json" \
  -d '{"auto_publish_enabled": false}' | jq

Expect: HTTP 200, body:
  { "ok": true, "auto_publish_enabled": false }

Now re-run TEST 5 with a fresh agent_content_id — the payload will still
pass all quality checks but will be stored as "flagged" because auto-publish
is disabled. Toggle it back on with:
  {"auto_publish_enabled": true}


================================================================================
 TEST 13 — POST /api/admin/upload -> image upload (requires CLOUDINARY_URL)
================================================================================
curl -s -X POST "$BASE_URL/api/admin/upload" \
  -H "Cookie: $ADMIN_COOKIE" \
  -F "file=@/path/to/test-image.jpg" | jq

Expect: HTTP 200, body:
  {
    "url": "https://res.cloudinary.com/.../seo-blogs/...",
    "width": <number>,
    "height": <number>,
    "cloudinary_public_id": "seo-blogs/..."
  }

Error cases:
  - No cookie / invalid session -> 401 Unauthorized
  - CLOUDINARY_URL not set -> 501 with actionable error message
  - Non-image file type -> 400 "Unsupported file type"
  - File > 8 MB -> 400 "File is ... MB. Maximum allowed is 8 MB."

================================================================================
 CLEANUP (optional)
================================================================================
Posts created by TEST 5/7/8/9/10 live in the `posts` table. Review/approve/reject
them via the admin UI (http://localhost:3000/admin, after logging in), or
delete directly:

  bun -e "
  const { db } = await import('./src/db/index.ts');
  const { posts } = await import('./src/db/schema.ts');
  const { inArray } = await import('drizzle-orm');
  await db.delete(posts).where(inArray(posts.agentContentId, [
    'agent-demo-content-marketing-strategy-01',
    'agent-demo-content-marketing-strategy-02-draft',
    'agent-demo-thin-content-01',
    'agent-demo-modular-content-01',
    'agent-demo-legacy-content-body-01',
  ]));
  console.log('cleaned up');
  "
